# Комментарии и документация кода на русском

Все комментарии и JSDoc в коде пишутся на русском — так устроен весь репозиторий:
интерфейс, документация и комментарии на русском, код и идентификаторы — на английском.

## Язык и тон

- Комментарий отвечает на вопрос **«зачем/почему»**, а не «что». Код и так показывает,
  что происходит; пояснять нужно замысел, ограничение или договорённость.
- Полное предложение: с заглавной буквы, в конце — точка.
- Тире — «—» с пробелами, буква «ё» — на месте.
- Технические термины не переводить: `localStorage`, `backend`, `SSE`, `Server Component`,
  `Turbopack` — латиницей, в силу привычности терминов.
- Имена файлов, типов и полей из кода — в бэктиках: `` `remoteId` ``, `` `chat_id` ``.

## Документирование компонентов (JSDoc/TSDoc)

Каждый компонент сопровождается JSDoc-блоком перед объявлением: описание
(что делает и в чём особенность — например, Server Component и статический
рендеринг), затем теги `@param` и `@returns`:

```tsx
import type { ReactNode } from "react";

interface CardProps {
  /** Заголовок карточки, отображается жирным шрифтом. */
  title: string;
  /** Дочерние элементы для рендеринга внутри тела карточки. */
  children: ReactNode;
}

/**
 * Карточка продукта (Server Component по умолчанию).
 * Рендерится статически на этапе сборки Next.js 16, клиентского JS не добавляет.
 *
 * @param props - Пропсы компонента.
 * @returns Разметку карточки с заголовком и телом.
 */
export function ProductCard({ title, children }: CardProps) {
  return (
    <div className="rounded-xl border p-4 shadow-sm">
      <h3 className="mb-2 text-lg font-bold">{title}</h3>
      <div>{children}</div>
    </div>
  );
}
```

- Пропсы описываются в интерфейсе перед компонентом: **каждое поле — однострочный
  JSDoc-комментарий** (TypeScript-эквивалент `@property` из `@typedef`).
- `@param props` — одним предложением; деталей не нужно — они в комментариях полей.
- `@returns` — что компонент возвращает, одним предложением.
- Для клиентских компонентов в JSDoc указывается причина (`'use client'`: state,
  эффекты, браузерные события).

## Документирование функций

- Экспортируемая функция — JSDoc до объявления. Для простой функции достаточно
  однострочного:
  ```ts
  /** Сохраняет чат и поднимает его в начало списка (последний активный — сверху). */
  export function saveChat(next: Chat, options: SaveOptions = {}): Chat {
  ```
- Для функции со сложным контрактом — многострочный блок с `@param` и `@returns`:
  ```ts
  /**
   * Отправляет запрос к backend и читает потоковый ответ.
   *
   * @param chatId - id чата на backend; создаётся заранее через `ensureRemoteChat`.
   * @param onDelta - Колбэк инкрементального текста для стриминга в UI.
   * @returns Полный текст ответа ассистента.
   */
  ```
- Неочевидные поля типов — однострочный JSDoc:
  ```ts
  /** id чата на backend; создаётся при первом запросе к серверу. */
  remoteId?: number;
  ```

## Комментарии внутри JSX (разметка)

Внутри JSX используется синтаксис фигурных скобок с блоком-комментарием:

```tsx
return (
  <main>
    {/* Turbopack вырезает JSX-комментарии из продакшен-сборки. */}
    <h1>Добро пожаловать</h1>
  </main>
);
```

- В JSX такие комментарии поясняют смысл секции разметки или неочевидное решение,
  а не пересказывают теги.
- Между `{/* … */}` и `//` внутри JSX разницы в действии нет, но для единообразия
  используется только форма `{/* … */}`.

## Inline-комментарии и служебные случаи

- **Inline `//`** — для неочевидных решений, ограничений платформы и связи
  с контрактом backend:
  ```ts
  // Черновик живёт в localStorage: прочитать его можно только на клиенте.
  ```
- **eslint-disable** — директиву оставлять, а объяснение давать комментарием строкой выше.
- **TODO/FIXME** — в формате `// TODO: что нужно сделать.` с точкой в конце;
  ссылку на задачу добавлять, если она есть.

## Чего не делать

- Не оставлять закомментированный код — удалять.
- Не писать шумные комментарии, дублирующие код (`// устанавливаем состояние`).
- Не подписывать автора, дату и ссылки на задачи без причины.
- Не смешивать языки: no mixed english comments like this one.
- Не дублировать в JSDoc типы из сигнатуры: описание говорит о назначении,
  а не повторяет `string` / `boolean`.
- Не переводить сообщения об ошибках пользователя внутри комментариев — они живут
  в коде строками, а комментарий поясняет поведение, а не повторяет текст.
